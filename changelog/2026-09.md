# SWEET_python Changelog — September 2026

**Highlights:** The annual model was charging a flare's inefficiency twice — a
hardcoded 2% slip stacked on top of a `flaring` destruction efficiency that
already accounted for it — which also made the annual engine disagree with the
monthly one by ~3.7% on identical inputs. A site with gas capture now emits
about 3.5% less; sites without capture are unaffected. Separately,
`gas_capture_efficiency` is now bounded to [0, 1] on both advanced-DST paths,
where an out-of-range value used to produce negative emissions silently. The
city-level advanced DST also gains a `food_waste_prevention` input, so callers
stop having to pre-shrink the waste stream themselves, and can now ask it where
the tonnage went — per waste type and per landfill — instead of re-deriving the
diversion split.

## Added

- **The city-level advanced DST can report its mass flow.**
  `run_advanced_dst_city(request, with_mass_flow=True)` adds a `mass_flow` key
  describing where the tonnage went, per variant and per year: `generated` (per
  waste type, before food waste prevention), `prevented`, `diverted` (per
  pathway per waste type, net of reject rates), `landfilled` (the residual), and
  `sites` (per landfill, in request order, windowed by open/close years). These
  are the frames the emissions were computed from — every one was already built
  and all but the residual's sign check discarded — so a caller rendering this
  is showing the model rather than a parallel estimate of it. That matters most
  for `diverted`: compost and anaerobic digestion draw only on organics and
  recycling only on recyclables, each with its own per-component reject rate, so
  the split is per waste type and cannot be approximated as one scalar on the
  total without composting metal and glass. A pathway the request never uses is
  omitted rather than sent as zeros; a missing pathway reads as zero. Default
  behaviour, the existing signature, and the existing return are unchanged.

- **`food_waste_prevention` on the city-level advanced DST.** A
  `{year: fraction}` series on `AdvancedDSTCityRequest` that removes a share of
  the city's generated food waste before anything else in the model reads the
  stream: food mass falls by that share, no other material's tonnage moves, and
  the total shrinks by exactly the food removed, with the composition
  renormalized around the smaller stream. Same lever as the city DST's
  `food_waste_prevention` (`City.implement_dst_changes_simple_v1_5`). It is
  generation-side, so it lands upstream of diversion — each pathway then takes
  its share of the smaller stream, and a pathway left without the organics to
  meet its target raises `over_diversion` rather than modelling negative
  landfilled mass. Values outside [0, 1] are clamped, matching how this module
  already treats `gas_capture_efficiency`.

  The reason it belongs here rather than in the caller: prevention is two
  coordinated edits — shrink the total, reshape the fractions — and they only
  stay in step if both are derived from *one* composition. A caller holding both
  a city composition and a site composition can pair a total scaled on one with
  fractions taken from the other, which moves the non-food masses and invents
  tonnage out of nothing. WasteMAP's ADST did exactly that. The model reads a
  single composition per request, so the two cannot disagree; the transform runs
  in mass space (multiply out, remove the food, divide back) so that the pairing
  is not expressible. **No output change** for any request that omits the field,
  which returns the inputs untouched.
  ([#54](https://github.com/RMI/SWEET_python/pull/54))

## Fixed

- **The annual model charged flare inefficiency twice, and disagreed with the
  monthly model.** `ch4_capture` is already `generation × capture_efficiency ×
  flaring`, so the gas a flare fails to destroy is emitted through the
  `(ch4_produce - ch4_capture)` residual. `estimate_emissions2` added
  `+ ch4_capture * 0.02` on top of that, charging the same 2% a second time.
  The monthly path (`trace_monthly`, used by the Climate TRACE per-site runs)
  has never had the extra term, so the same inputs produced ~3.7% higher
  emissions on every DST path than on the TRACE path. The term is removed and
  the two engines now agree exactly across the full grid of capture × flaring
  combinations. **Model-output change:** a site with gas capture emits ~3.5%
  less at the default flaring of 0.98. Sites without capture are byte-for-byte
  unchanged — with `gas_capture_efficiency` at 0 the removed term was already 0.
  ([#51](https://github.com/RMI/SWEET_python/pull/51))

- **`gas_capture_efficiency` is bounded to [0, 1].** It is typed as a bare
  `Dict[int, float]` on both advanced-DST request models, nothing validated it,
  and the engine multiplied straight through — so `1.5` silently produced
  negative emissions and a negative value manufactured methane. Both runners now
  clip the resolved series. No output change for any in-range input.
  ([#51](https://github.com/RMI/SWEET_python/pull/51))

- **One methane density constant.** `landfill.py` carried both `0.7168` kg/m³
  and `0.657` for the same m³↔kg conversion — 9.1% apart, CH₄ at 0 °C versus at
  roughly 25 °C. Unified as `CH4_DENSITY_KG_PER_M3 = 0.7168`, the value the rest
  of SWEET already uses and the basis `L_0` is denominated in. No output change:
  the `0.657` sat in the `doing_fancy_ox` branch, which is unreachable because
  `doing_fancy_ox` is hardcoded `False` with its enabling logic commented out.
  ([#51](https://github.com/RMI/SWEET_python/pull/51))

## Known limitations

- **Collected gas that is vented is still oxidised as if it left through the
  cover.** It left through a stack. At `capture 0.6`, `oxidation 0.22` and
  `flaring 0`, the model gives `0.78 × generation` where the physical answer is
  `0.912 ×`. Only reachable by setting `flaring` near zero, which the 0.98
  default makes rare; pinned by a test so it stays a decision rather than an
  accident. ([#51](https://github.com/RMI/SWEET_python/pull/51))

- **The two engines still give `captured` different meanings** — collected gas
  in the annual path (`generation × efficiency`), destroyed gas in the monthly
  one (`× flaring` as well). Unifying that changes a reported quantity with
  consumers outside this repo, so it wants its own change.
  ([#51](https://github.com/RMI/SWEET_python/pull/51))
