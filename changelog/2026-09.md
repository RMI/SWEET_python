# SWEET_python Changelog — September 2026

**Highlights:** Model output frames now come out with their waste-type columns
in one fixed order instead of a per-process one — a `set` fed the ordering, and
Python randomizes set iteration per process, so the same code on the same inputs
diffed dirty against itself. Values move in the last bit only, where a sum runs
across the reordered columns. Earlier in the month: the
annual model was charging a flare's inefficiency twice — a
hardcoded 2% slip stacked on top of a `flaring` destruction efficiency that
already accounted for it — which also made the annual engine disagree with the
monthly one by ~3.7% on identical inputs. A site with gas capture now emits
about 3.5% less; sites without capture are unaffected. Separately,
`gas_capture_efficiency` is now bounded to [0, 1] on both advanced-DST paths,
where an out-of-range value used to produce negative emissions silently. The
city DST's diversion sum also stops passing pandas a keyword pandas is removing,
which would have broken the model path on pandas 4 with an error pointing
nowhere near the cause.

## Changed

- **`DivsDF.sum` no longer passes `copy=False` to `infer_objects`.** The four
  `reindex(...).infer_objects(...).fillna(0)` chains that combine the compost /
  anaerobic / combustion / recycling streams into the diverted-mass frame passed
  a keyword pandas has ignored since 3.0 made Copy-on-Write unconditional —
  `infer_objects` hands it to `_check_copy_deprecation`, which warns and returns,
  and nothing else in the method reads it. It emitted 96 `Pandas4Warning`s per
  test run, and pandas 4 removes it, at which point the call raises `TypeError`.
  That break would have been worse than a `TypeError`: all three callers wrap
  `divs_df.sum()` in a bare `except:` whose fallback, `sum(divs_df.values())`,
  does not work on a pydantic model, so the failure would have surfaced as
  `AttributeError: 'DivsDF' object has no attribute 'values'`. A new test
  simulates the removal and pins both the sum and that caller.
  `infer_objects()` itself is kept — not for the reindex, which never produces an
  object column (added columns arrive as float64 NaN whatever the source dtypes),
  but to stop an object-dtype *input* column from surviving `fillna(0)` and
  dragging the summed frame with it. **No output change**, verified end to end:
  five city-DST scenarios, including the food-waste-prevention path that drives
  this code, produce a byte-identical dump of 73,760 numbers across 165 model
  outputs before and after.
  ([#62](https://github.com/RMI/SWEET_python/pull/62))


city-level advanced DST also gains a `food_waste_prevention` input, so callers
stop having to pre-shrink the waste stream themselves, and can now ask it where
the tonnage went — the diversion split per waste type, and the total each
landfill received — instead of re-deriving it.

## Added

- **A disposal site can accept waste the city did not send it.** `CityLandfillSpec`
  takes an optional `accepted_waste_mass`: everything crossing that site's
  weighbridge in a year, from every source. `landfill_split_timeline` is
  fractions that must sum to 1, so until now every ton at every site came from
  the city by construction — a regional landfill taking waste from a
  neighbouring municipality was structurally unsayable, and site operators know
  their gate total rather than one city's share of it.

  Whatever the stated total exceeds the city's own allocation is modelled as a
  second stream at the same site: its own `Landfill`, its own pass through the
  decay kernel, deposited and windowed on exactly the same terms as the city's
  waste because it is the same hole in the ground. A figure at or below the
  city's allocation is read as "no waste from outside" rather than as a
  reduction of the city's — the city's waste still has to go somewhere, and this
  does not add anywhere else for it to go.

  **The city's own emissions do not move**, and the reason is structural rather
  than arithmetic: `City.sum_landfill_emissions` sums `parameters.landfills`,
  and the surplus landfills are never put in that list. The test asserts frame
  equality, not a tolerance. Every request without the field takes the path it
  took before, with `city_params.py` untouched.

  `run_advanced_dst_city(request, with_site_emissions=True)` returns the split:
  per landfill in request order, `city`, `other` and `total` in tons of methane
  per year. The two are separate kernel runs summed, never a ratio applied to
  one of them — this year's emissions come from decades of deposit cohorts each
  with their own split, and attributing by this year's tonnage was measured at
  up to 28% error where a site's mix of sources moves over time. A test pins
  that case so the shortcut cannot be reintroduced quietly.

  Superposition is exact because the kernel is linear in deposited mass
  (measured at ~1e-16 relative; `E(0)` is exactly `0.0`), so "the city's share
  of this site's methane" is a measured quantity rather than an allocation
  convention. `Landfill.doing_fancy_ox` is the one thing that would break it —
  its body is genuinely nonlinear in mass — so the split now refuses to run
  rather than silently returning an attribution nobody could defend.

  The surplus carries the city's post-diversion residual composition. That is a
  modelling default, not a numerical constraint: `k` is city-wide, so a stream's
  own mix moves only its per-component masses. It is the default because a gate
  observation is downstream of whatever diversion happened upstream of it.
  `site_inflow.residual_composition` is the single function a later "a site
  states its own mix" change replaces. In a year the city buries nothing that
  mix is 0/0, and the fallback is the composition **as shares** — the
  composition as masses is all-zero in exactly the years it would be needed,
  which left the surplus with a zero mix and deposited none of it. A site taking
  regional waste while its city has not started collecting yet is an ordinary
  shape, and it silently lost every ton: 200,000 t/yr over thirty years came
  back as 0 t CH4. Pinned by test.

  New behaviour lives in `SWEET_python/site_inflow.py`, following the convention
  `dst_common.build_landfill` already sets — a landfill's construction lives
  outside `landfill.py` — rather than growing the 9,000-line `city_params.py`.
  ([#65](https://github.com/RMI/SWEET_python/pull/65))

- **`run_advanced_dst_city_limits` — what a city's composition allows.** Takes
  the same request as `run_advanced_dst_city` and returns, per year: the
  fraction of each waste component's own mass the diversion pathways claim, the
  component that maximum falls on, the largest fraction each pathway could take
  with the others held where they are, and the largest food-waste-prevention
  share the year's diversion demand leaves room for.

  The point is that the component sets come from `city.div_components` — the
  same ones `_diverted_masses` splits on — so a caller enforcing these bounds
  cannot drift from the arithmetic the model performs. WasteMAP's ADST had been
  keeping its own copy of the organic/recyclable component lists in TypeScript.

  Closed-form, not a search: the split across a pathway's components is
  proportional to the composition, so pathway `p` consumes `divfrac_p / D_p` of
  every component it touches and the per-component claims add. Stated per
  component rather than as two pools, since the pathways do not partition into
  two — compost and anaerobic digestion share a set, recycling overlaps it on
  wood and paper, and combustion draws on all ten.

  It bounds **gross** diversion, before reject rates — the same basis
  `over_diversion` now measures on, so the two are deliberately the same
  boundary and a caller respecting these limits cannot produce a request the
  model rejects on mass balance.

  Returns `{"baseline": {...}, "scenario": {...}}`, because the model runs both
  variants and enforces `over_diversion` on each. The scenario's composition,
  tonnage, prevention and diversion all take effect from `implement_year`, so
  one set of bounds taken from the baseline left every scenario year
  unbounded — a city whose scenario drops its food share from 20% to 5% was
  told compost could still take 20% of the stream, and the model then refused
  the request the caller had been cleared to make. Every scenario series is
  spliced at `implement_year` the same way the model splices it, so a variant's
  pre-implement bounds are its baseline's by construction.

  Each variant also carries `starved_pathways`, a years x pathways mask marking
  where a pathway is asked for material the city generates none of. That is the
  one case `component_use` cannot express — with the pool at zero the claim is
  `0/0`, which reads as zero rather than as too much — so a caller reading
  `component_use` alone would call such a request comfortably feasible.
  `max_diversion` already comes to nil there, so a caller enforcing that never
  arrives; the mask says why.

  Read-only; no existing behaviour changes.
  ([#58](https://github.com/RMI/SWEET_python/pull/58),
  [RMI/WasteMAP#777](https://github.com/RMI/WasteMAP/pull/777))

- **The city-level advanced DST can report its mass flow.**
  `run_advanced_dst_city(request, with_mass_flow=True)` adds a `mass_flow` key
  describing where the tonnage went, per variant and per year: `generated` (per
  waste type, before food waste prevention), `prevented`, `diverted` (per
  pathway per waste type, net of reject rates), `landfilled` (the residual), and
  `sites` (per landfill, in request order, windowed by open/close years). These
  are the frames the emissions were computed from — every one was already built
  and all but the residual's sign check discarded — so a caller rendering this
  is showing the model rather than a parallel estimate of it. That matters most
  for `diverted`: compost and anaerobic digestion draw only on organics and
  recycling only on recyclables, each with its own per-component reject rate, so
  the split is per waste type and cannot be approximated as one scalar on the
  total without composting metal and glass. A pathway the request never uses is
  omitted rather than sent as zeros; a missing pathway reads as zero. The new
  argument is keyword-only and defaults to off, so existing calls are
  unaffected and the default return is unchanged — but the signature itself did
  gain a parameter, which a caller comparing versions will see.
  ([#55](https://github.com/RMI/SWEET_python/pull/55))

- **`food_waste_prevention` on the city-level advanced DST.** A
  `{year: fraction}` series on `AdvancedDSTCityRequest` that removes a share of
  the city's generated food waste before anything else in the model reads the
  stream: food mass falls by that share, no other material's tonnage moves, and
  the total shrinks by exactly the food removed, with the composition
  renormalized around the smaller stream. Same lever as the city DST's
  `food_waste_prevention` (`City.implement_dst_changes_simple_v1_5`). It is
  generation-side, so it lands upstream of diversion — each pathway then takes
  its share of the smaller stream, and a pathway left without the organics to
  meet its target raises `over_diversion` rather than modelling negative
  landfilled mass. Values outside [0, 1] are clamped, matching how this module
  already treats `gas_capture_efficiency`.

  The reason it belongs here rather than in the caller: prevention is two
  coordinated edits — shrink the total, reshape the fractions — and they only
  stay in step if both are derived from *one* composition. A caller holding both
  a city composition and a site composition can pair a total scaled on one with
  fractions taken from the other, which moves the non-food masses and invents
  tonnage out of nothing. WasteMAP's ADST did exactly that. The model reads a
  single composition per request, so the two cannot disagree; the transform runs
  in mass space (multiply out, remove the food, divide back) so that the pairing
  is not expressible. **Model-output change** wherever the field is set: the
  prevented tonnage leaves the stream before diversion, so masses and the
  emissions derived from them both move. **No output change** for any request
  that omits it, which returns the inputs untouched.
  ([#54](https://github.com/RMI/SWEET_python/pull/54))

## Added

- **The city-level advanced DST can model an incineration facility.**
  `CityLandfillSpec.combusts` marks a facility as burning the waste routed to
  it — incineration, with or without energy recovery — rather than depositing
  it. The share of the city's disposed waste sent there still arrives there,
  but only the unburnable reject (`City.combustion_reject_rate`, 10%) is
  deposited and left to decay; the rest is destroyed and, since combustion
  produces no methane in this model, emits nothing. The burnt share is not
  re-routed to another site. The remaining per-site fields then describe the
  residue: `landfill_type` is the residue's disposal category, and the
  gas/biocover fields are the residue pile's.

  `combusts` is a `Variant`, so a facility can start or stop burning at
  `implement_year` — which is what a caller needs to model converting a dump
  into an incinerator, or retiring one. It is optional and defaults to a
  depositing site, so an existing caller is byte-identical.

  The endpoint previously had no notion of burning at all, so a caller
  describing an incinerator could only submit it as an ordinary landfill: the
  facility decayed 100% of its intake and reported methane an incinerator
  cannot physically produce. `City.sdst_v1_5` has always handled a
  waste-to-energy site correctly — combustion at 100% of intake for every open
  year, with the 10% reject landfilled — so this brings the city-level path to
  parity with the single-site one
  (`advanced_dst_city.py`, `tests/test_adst_city_incineration.py`). ([#53](https://github.com/RMI/SWEET_python/pull/53))


## Fixed

- **Model output column order no longer depends on `PYTHONHASHSEED`.**
  `City.components` and the values of `City.div_components` were plain `set`s.
  A set is the right shape for eligibility — that is a membership question — but
  they are also what the engines iterate to build DataFrame columns, and a `set`
  of `str` iterates in hash order, which Python randomizes per process (PEP 456).
  The same code on the same inputs therefore produced a different column order in
  every process: 356 of 749 dumped model outputs changed order between two seeds.
  `WASTE_TYPES` in `constants.py` is now the single definition of the order — the
  field order of `WasteFractions`/`WasteMasses`, so the frames built from a
  pydantic `model_dump()` and the frames built from an eligibility set finally
  agree — and `WasteTypeSet` is a `frozenset` that iterates in it, which makes all
  35 `list(...)` conversions and 45 iterations deterministic without touching a
  call site (including the Climate TRACE pipeline's, which reach into the same
  attributes). `advanced_dst_city` moves off its lone alphabetical `sorted()` onto
  the same order.

  **Deterministic across hash seeds:** 749 outputs / 297,806 numbers dumped at
  full precision are byte-identical across three hash seeds, where 356 of those
  749 changed column order between two seeds before.

  **Against the previous code, values move in the last bit only.** Anywhere a
  sum runs *across* the waste-type columns, reordering them changes the result
  by an ULP or so, because floating-point addition is not associative. Two
  places: the derived `total` column (307 cells at one seed, 1 ULP each), and
  `_diverted_masses` in `advanced_dst_city`, where `denom = sub.sum(axis=1)` is
  the pool a pathway draws on and divides into its mass. Measured on a city
  diverting to compost, recycling and combustion, canonical order against the
  old alphabetical one: per-component diverted mass moves by up to 1.5e-16
  relative (9.1e-13 t on a 137,414 t/yr city) and modelled emissions by up to
  8.9e-16. So this is not a no-op against the old outputs — it is a 1-ULP
  change, in exchange for the same numbers in every process.
  ([#63](https://github.com/RMI/SWEET_python/pull/63))

- **Over-diversion is measured before rejection.** The guard compared *net*
  diverted mass against what the city generates, but rejects stay in the waste
  stream and are landfilled as their own material — so a pathway fed more of a
  material than exists still left a positive residual once the rejects came
  back, and passed. A city could recycle a third more paper than it generates
  and then landfill the rejects of paper that was never there.
  `_diverted_masses` now returns both bases: `net` still drives the landfilled
  residual and the mass flow, and `gross` drives the guard. The error message
  names the material and the year that ran out instead of only saying
  "over-diversion".

  This is the same boundary `run_advanced_dst_city_limits` reports, on purpose:
  the caps a caller enforces and the check the model performs are now one rule.
  It is a tightening — a request that over-diverted on the gross basis and was
  rescued by its own reject rates will now be refused. **No output change for
  any request that passes**, and none of WasteMAP's three ADST samples is
  affected, since its own slider caps were already on the gross basis.

- **A diversion pathway with no material to process says so.** Asked to compost
  15% of a stream with no organics in it, `_diverted_masses` divided the pool's
  size into the pathway's mass — 0/0 — zeroed the result, and composted none of
  the stream while reporting success. It now raises
  `diversion_without_material`, naming the pathway and the components it can
  process. It is the degenerate end of over-diversion (a positive share of a
  pool of size zero) and it was the one place the claim ratio jumped: continuous
  right up to an empty pool, then silently nothing.
  ([#59](https://github.com/RMI/SWEET_python/pull/59),
  [RMI/WasteMAP#778](https://github.com/RMI/WasteMAP/pull/778))


- **The landfill split is renormalized over the landfills actually accepting
  waste.** `landfill_split_timeline` says how the post-diversion stream divides
  across landfills, but a landfill only accepts waste inside its own window —
  and a closure year is not an intake year. A share pointed at a landfill that
  is shut is not a share of anything: the mass was scaled onto that landfill and
  then zeroed by `apply_window`, so it left the model entirely. The shares are
  meant to account for *all* the post-diversion waste, so they are now gated to
  the open landfills and renormalized over them, per variant (a `siteClosure`
  intervention moves the scenario's windows).

  The sum-to-1 check moved to the submitted shares, before renormalization —
  afterwards every year is exactly 1 or exactly 0 by construction — and a year
  in which *no* landfill is open is now exempt from it. There is nowhere for
  that waste to go, so no set of shares can account for it, and requiring one
  forced callers to name a destination that does not exist.

  **No output change for a caller that already zeroed shut landfills and
  normalized over the rest**, which is provable rather than hoped: the gate is
  then satisfied and the row sums are 1, so the transform is the identity.
  Checked against the three WasteMAP ADST samples — Washington DC and Mexico
  City submit no share on a shut landfill in any year, and Bandung's shares in
  its 30 years with nothing open were being discarded before and are zeroed now.
  A caller that *was* losing mass this way gains it back.

  The same check now also requires each share to lie in `[0, 1]`, not merely to
  sum to 1. `[-0.5, 1.5]` summed to exactly 1 and passed, then scaled a
  negative mass onto the first landfill and buried it there — a site
  accumulating negative stock. Nothing downstream refused it:
  `create_advanced` multiplies straight through and `over_diversion` measures
  the city's residual before the split is applied. A request like that is now
  an `invalid_parameters` error naming the year and the landfill.

  And the pre-implement half of the scenario split is spliced to baseline
  *before* it is validated, rather than after. Those rows are never used —
  scenario tracks baseline until changes take effect — so a caller who left
  them malformed was being rejected for a number the model then discarded.
  Renormalization had the same ordering problem, but its result was overwritten
  by the splice, so only the error was observable. Shares from `implement_year`
  onward are validated exactly as before.
  ([#57](https://github.com/RMI/SWEET_python/pull/57),
  [RMI/WasteMAP#776](https://github.com/RMI/WasteMAP/pull/776))



- **A caller can now say a landfill never closes.** `MODEL_YEAR_MAX` was the
  hard ceiling on `landfill_open_close`, but a closure year is not an intake
  year (`apply_window` zeroes from it inclusive), so a site submitted as closing
  in `MODEL_END_YEAR` accepts nothing in the model's *final* year — meaning
  `MODEL_END_YEAR` could not express "no known closure", and there was nothing
  else to send. `dst_common.NEVER_CLOSES` (`MODEL_END_YEAR + 1`) is now
  admissible and means exactly that. It is the same sentinel `city_params`
  already uses for a missing recorded close year (`fillna(MODEL_END_YEAR + 1)`),
  so the two paths now agree.

  `apply_window` is the only consumer of a close year on the advanced paths
  (`Landfill` merely stores it), and `windowed.loc[2051:]` is a no-op against an
  index ending at 2050 — so this is purely permissive. **No output change for
  any request that does not use the new value**; a request that switches to it
  gains the final year's deposits, which every ADST city had been discarding.
  The boundary itself is unchanged and now documented on `apply_window` as the
  definition, cross-referencing `city_params` and Climate TRACE's
  `time_series_ops.zero_incoming_waste_from_close_year`.
  ([#56](https://github.com/RMI/SWEET_python/pull/56),
  [RMI/WasteMAP#775](https://github.com/RMI/WasteMAP/pull/775))



- **The annual model charged flare inefficiency twice, and disagreed with the
  monthly model.** `ch4_capture` is already `generation × capture_efficiency ×
  flaring`, so the gas a flare fails to destroy is emitted through the
  `(ch4_produce - ch4_capture)` residual. `estimate_emissions2` added
  `+ ch4_capture * 0.02` on top of that, charging the same 2% a second time.
  The monthly path (`trace_monthly`, used by the Climate TRACE per-site runs)
  has never had the extra term, so the same inputs produced ~3.7% higher
  emissions on every DST path than on the TRACE path. The term is removed and
  the two engines now agree exactly across the full grid of capture × flaring
  combinations. **Model-output change:** a site with gas capture emits ~3.5%
  less at the default flaring of 0.98. Sites without capture are byte-for-byte
  unchanged — with `gas_capture_efficiency` at 0 the removed term was already 0.
  ([#51](https://github.com/RMI/SWEET_python/pull/51))

- **`gas_capture_efficiency` is bounded to [0, 1].** It is typed as a bare
  `Dict[int, float]` on both advanced-DST request models, nothing validated it,
  and the engine multiplied straight through — so `1.5` silently produced
  negative emissions and a negative value manufactured methane. Both runners now
  clip the resolved series. No output change for any in-range input.
  ([#51](https://github.com/RMI/SWEET_python/pull/51))

- **One methane density constant.** `landfill.py` carried both `0.7168` kg/m³
  and `0.657` for the same m³↔kg conversion — 9.1% apart, CH₄ at 0 °C versus at
  roughly 25 °C. Unified as `CH4_DENSITY_KG_PER_M3 = 0.7168`, the value the rest
  of SWEET already uses and the basis `L_0` is denominated in. No output change:
  the `0.657` sat in the `doing_fancy_ox` branch, which is unreachable because
  `doing_fancy_ox` is hardcoded `False` with its enabling logic commented out.
  ([#51](https://github.com/RMI/SWEET_python/pull/51))

- **A scenario opening a landfill later than the baseline lost the waste
  buried before it — in years the scenario is supposed to match the baseline
  exactly.** The city-level advanced DST runs two variants and splices them:
  the scenario's own inputs take effect at `implement_year`, and every earlier
  year is the baseline's. A landfill's open/close window is per variant,
  because a `siteClosure` intervention moves it, and two things applied the
  scenario's window to years that convention had already assigned to the
  baseline.

  `mass_scen` took the baseline's pre-implement rows and *then* had the
  scenario's window applied, so `apply_window` zeroed the mass that had just
  been spliced in. And the model derives its year range from the landfill's
  `open_date` (`model_v2.estimate_emissions2`), so starting the scenario's
  landfill at the scenario's own open year dropped those years from its
  emissions frame altogether — the two halves came back a different shape, and
  a caller subtracting them got a `KeyError` or a silently truncated diff.

  Each variant is now windowed on its own years first and the splice comes
  after, and the scenario's landfill starts at `min(baseline_open,
  scenario_open)` — the earliest year its mass frame can carry anything. The
  parameter vectors already span the wider range, which is the contract
  `estimate_emissions2` documents for its caller.

  **Modeled scenario emissions rise for any request whose scenario states a
  later opening year than its baseline**, by the decay tail of the waste those
  years bury; a site opened in 1980 and restated as 2010 was missing thirty
  years of accumulated stock. Verified on a 100,000 t/yr city: baseline's
  frame ran 1980–2050 and the scenario's 2010–2050, diverging by up to 593 on
  the fifteen pre-implement years they did share. Nothing changes when the two
  windows agree, which is the ordinary case — a request with no `siteClosure`
  and no scenario open/close of its own is byte-identical.
  ([#60](https://github.com/RMI/SWEET_python/pull/60))


## Known limitations

- **`DivsDF.sum()` still orders its columns alphabetically.** It builds them with
  `Index.union`, which sorts, so that frame and the `waste_mass_df` derived from
  it use a different order from the rest of the model. Deterministic, so it was
  never part of the hash-seed problem, and it affects nothing downstream because
  every consumer of `waste_mass_df` slices it by name — but it is a second order,
  pinned by a test until it can be unified.
  ([#63](https://github.com/RMI/SWEET_python/pull/63))


- **An incineration facility's residue carries the city's waste
  composition**, exactly as the combustion diversion pathway's reject always
  has. Real incinerator bottom ash is far more inert than that, so the
  residue's methane is an overestimate. Giving the reject its own composition
  changes the diversion pathway too, not just `combusts`, so it wants its own
  change. ([#53](https://github.com/RMI/SWEET_python/pull/53))

- **The single-site `advanced_dst` path cannot model incineration.** Its
  `waste_mass` is documented as the final landfilled mass, so combustion
  belongs upstream of it; only `adst_city_level` grew `combusts`. The ADST
  frontend calls the city-level endpoint for both its city and site modes, so
  nothing user-facing depends on this. ([#53](https://github.com/RMI/SWEET_python/pull/53))


- **Collected gas that is vented is still oxidised as if it left through the
  cover.** It left through a stack. At `capture 0.6`, `oxidation 0.22` and
  `flaring 0`, the model gives `0.78 × generation` where the physical answer is
  `0.912 ×`. Only reachable by setting `flaring` near zero, which the 0.98
  default makes rare; pinned by a test so it stays a decision rather than an
  accident. ([#51](https://github.com/RMI/SWEET_python/pull/51))

- **The two engines still give `captured` different meanings** — collected gas
  in the annual path (`generation × efficiency`), destroyed gas in the monthly
  one (`× flaring` as well). Unifying that changes a reported quantity with
  consumers outside this repo, so it wants its own change.
  ([#51](https://github.com/RMI/SWEET_python/pull/51))
